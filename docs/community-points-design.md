# 社区积分账本与多签支出设计

首版在 Rice 和 PostgreSQL 中统一管理社区积分。社区发行积分资产，个人、节点和系统各自持有账户。第三方应用可以发起付款请求，由 Rice 完成授权和记账。社区金库可以要求多名签署人共同批准支出。

## 积分资产与账本

每种积分用稳定的 `point_id` 标识。不同社区可以发行同名积分。账户在积分资产内唯一标识持有人，handle 和 DID 可用于查找。金额按整数计量，单笔交易只涉及一种资产。跨资产兑换、积分过期和外部可验证签名留待后续定义。

| 表 | 职责 |
| --- | --- |
| `points` | 保存发行社区、积分代码及状态 |
| `point_accounts` | 标识资产下的个人、节点或系统账户 |
| `point_balances` | 保存可用余额和冻结余额 |
| `point_transactions`、`point_entries` | 保存交易和逐账户、逐余额类别的增减分录 |
| `point_recipients` | 保存同一笔交易中每项收款的账户、金额和独立备注 |
| `point_holds` | 关联冻结交易，记录初始额度和剩余可划扣额度 |
| `point_payment_intents` | 记录应用订单、收款账户、金额、有效期和入账结果 |

赠送 10 稻米时，付款账户可用余额减 10，收款账户可用余额加 10。冻结 10 稻米时，同一账户的可用余额减 10、冻结余额加 10。发行和回收由明确的系统账户记对向分录。退款新增交易并引用原付款，原分录保持不变。

记账在同一个数据库事务内锁定账户、检查余额、写入交易和分录并更新余额。单笔交易的分录合计为零，普通账户可用余额和所有账户的冻结余额均不得为负。部分划扣和释放的累计金额不得超过冻结额度，累计退款不得超过原付款金额。幂等键按调用方、资产及操作隔离，相同请求返回原结果，参数变化返回冲突。

## 积分发行

每个资产拥有独立发行策略和一个专用发行账户。新资产从 `draft` 开始，首次分配通过一笔 `initial_allocation` 交易直接入账给指定个人或社区金库，同时激活资产。允许零发行激活时，由发行治理明确确认并保存激活记录。后续通过 `mint` 交易增加供应。金库余额发给成员属于普通转账，总供应量不变。

| 入口 | 约定 |
| --- | --- |
| `POST /v1/points/{point_id}/issuances` | 社区发行管理员创建提案，提交 `kind`、发行原因和 `recipients`。每项含 `account_id`、正整数字符串 `amount` 和可选 `note`。接受 `Idempotency-Key`，返回发行提案 ID、总额和审批状态。 |
| `POST /v1/points/{point_id}/issuances/{id}/approvals` | 当前策略的签署人登录并二次验证后批准。达标时尝试执行，重复批准只计一次。 |
| `GET /v1/points/{point_id}/issuances/{id}` | 授权运营人员和签署人查进度。执行成功返回交易 ID，额度不足等错误保留明确原因。 |

用服务端环境变量 `POINT_ISSUANCE_PROPOSERS` 配置资产 ID 到提案人用户 ID 列表的 JSON 映射。未列出的资产默认拒绝外部创建发行提案。发行管理员可以提出申请。执行由发行策略决定，首版采用固定多签门槛，例如 2-of-3。签署资格按发行社区和资产隔离。签署人批准固定的资产、发行类型、完整分配清单、原因、策略版本和期限。更改参数须重新提案。普通钱包权限、节点支出多签及第三方应用凭证均不授予发行权限。社区治理负责建立首版策略，提高发行额度、变更签署人或降低门槛须由当前发行策略批准，旧待执行提案随策略换版失效。

资产发行配置可设累计发行上限。额度按累计发行计算，回收不恢复铸造额度。保存累计发行和累计销毁量，流通量按两者之差计算，包含普通钱包与金库的可用和冻结余额。未执行提案不预占额度。执行时锁定资产发行记录，重新检查当前策略、批准门槛、期限、资产状态、收款资格和剩余额度。初始分配只允许执行一次，两个并发提案也只能有一个成功。额度校验、发行计数、发行账户负分录、各收款账户正分录、余额和提案状态在同一事务提交。停用资产拒绝新增发行。同一提案只对应一笔交易，失败可查并按有效策略重试。

旧稻米迁移使用受控的期初入账路径，保留原累计发行和回收口径并对账，避免将历史余额再次计入新增发行。验收覆盖重复初始化、跨社区审批、第三方凭证调用、并发额度竞争和批量分配失败回滚。

## 批量付款与备注

一笔工资支出可以有一条公开备注「工资」、一条仅付款方授权人员可见的私有备注，以及多项收款明细。例如 A 收到 100 稻米，备注「一月份工资」，B 收到 40 稻米，备注「兼职补贴」。收款人只能看到自己的明细和交易公开备注。公开接口只返回明确允许公开的字段，应用的查单权限不自动授予私有备注的读取权限。

批量付款的收款明细、余额更新和分录在同一事务提交，任一收款项失败则整笔回滚。记账层校验收款金额合计与扣款总额一致，并按账户核对收款明细与贷方分录。多签提案和幂等请求摘要绑定完整收款清单、每项金额及备注。变更任何一项均需重新发起审批。签署人须能看到完整的付款清单。

## 第三方授权支付

首版采用托管确认页。第三方订单使用一种积分、一个预登记收款账户，只接受个人钱包付款。社区金库与节点钱包的批量支出走独立的多签流程。

运营人员登记应用名称、收款账户和完整 HTTPS 返回地址。首版可由服务端配置维护注册信息。每个应用使用独立、可撤销和轮换的服务端 Bearer 凭证，服务端仅保留凭证摘要。凭证归属决定应用身份，创建和查询均按该身份隔离。停用应用时禁止建单和未完成订单付款。

| 入口 | 约定 |
| --- | --- |
| `POST /v1/payment-intents` | 应用提交 `external_order_id`、`amount`。金额是大于零且不超过 bigint 上限的十进制整数字符串。返回 `id`、`status`、`amount`、`point_id`、`expires_at` 和 `checkout_url`。 |
| Rice 确认页 | 使用不可猜测的链接令牌定位订单。登录后展示应用、收款方和金额。确认使用带会话和 CSRF 防护的 POST，由服务器从当前用户推导个人账户。 |
| `GET /v1/payment-intents/{id}` | 应用查询自己的订单，成功时额外返回 `transaction_id`。其他应用的订单统一返回 404。 |

建单时冻结订单参数，包括收款账户、积分资产、金额和预登记返回地址。配置修改只影响新订单，应用停用和账户停用仍在确认时检查。以 `(app_id, external_order_id)` 去重。相同金额重试返回原订单及当前状态，金额不同返回 409。订单到期后重新支付需使用新订单号。

首版允许持有链接的登录用户用自己的个人钱包代付。链接本身不授予扣款权限，应用查单也不返回付款人的身份、余额或私有备注。Rice 仅跳回快照中的预登记地址，并附带订单 ID。应用以服务端查单的成功结果为交付依据，以订单 ID 去重交付。

付款时先锁订单，再以固定顺序锁账户。拿到锁后用当前时间检查订单是否有效，核对资产、账户状态、付款权限和余额。扣款、收款分录、收款明细与订单成功状态一起提交。并发确认只产生一笔入账。其他付款人对已完成订单只能看到订单已支付，不能取得原付款人的私有数据。

| 状态 | 行为 |
| --- | --- |
| `pending` | 可确认。余额不足时保持原状态，显示 `insufficient_balance`，可在到期前再次主动确认。 |
| `succeeded` | 终态。查单返回交易 ID，原付款人重复确认不会扣第二次。 |
| `expired` | 终态。服务端按截止时间判定，读写入口采用同一规则，无需依赖定时任务。 |
| `canceled` | 保留给显式取消。首版不提供取消接口，关闭页面后可在有效期内继续付款。 |

请求超时时先查同一订单。首版通过查单确认结果，Webhook、长期扣款授权和第三方退款接口后置。

参考 [Stripe 托管 Checkout](https://docs.stripe.com/payments/checkout/how-checkout-works?payment-ui=stripe-hosted)。

## 多签支出授权

策略绑定付款账户。个人钱包可单人确认，社区金库或节点钱包可设置 2-of-3 或 3-of-5。首版采用 Rice 登录与二次验证记录审批。后续若需独立验签，再定义密钥或 WebAuthn 签名的载荷、域和验签规则。

| 拟新增表 | 职责 |
| --- | --- |
| `point_spend_policies` | 记录付款账户、版本、批准门槛和适用动作 |
| `point_spend_policy_signers` | 保存各策略版本的签署人，同一身份在同一版本只计一次 |
| `point_spend_proposals` | 固定付款账户、收款账户、积分、金额、动作、期限、策略版本及业务引用 |
| `point_spend_approvals` | 记录签署人、批准时间和提案摘要，提案与签署人组合唯一 |

签署人独立确认同一份提案。变更金额或收款方需要新提案。策略变更后，旧版本待执行提案失效。降低门槛、更换签署人和关闭多签也须经当前策略批准。

首版待审批时不冻结积分。达到门槛后，Rice 锁定提案与付款账户，重新校验有效期、当前策略、批准人数和实时余额。扣款、入账、提案执行和订单成功在同一事务提交。重复执行最多入账一次。余额不足时记录执行失败原因并保留审批历史。审批端显示待审批、可执行、已执行、已失效及最近执行错误。余额不足后，由有权执行的签署人在提案有效期内主动重试。每个提案最多关联一笔执行交易。策略切换与提案执行共用账户锁，以锁内的当前版本决定是否允许记账。

所有能支出或承诺支出的入口都应校验账户策略，包括赠送、节点划拨及任务和活动冻结。批准冻结时，提案要固定用途、总额度和结算规则。符合规则的后续划扣可沿用该授权，扩大额度或变更规则之外的收款方需要重新审批。

## 现有稻米迁移与验收

存储迁移和批量转账已在本地验证。发行、冻结、多签审批、第三方 API 和旧数据回填按下列里程碑推进。

将稻米注册为首个积分资产，按账户建立期初分录，保留旧流水和凭证引用。未结冻结需要逐笔迁移剩余额度和任务或活动引用。切换前逐账户核对可用和冻结余额，并核对发行总量、未结冻结及旧交易映射。切换后由统一记账层负责写入。

## 开发里程碑

| 阶段 | 状态 | 交付与验收 |
| --- | --- | --- |
| M0 批量记账 | 已完成，本地验证 | 支持多收款人、独立金额和备注。验证余额、交易和分录原子提交，相同请求幂等，余额不足或中途失败整笔回滚。 |
| M1 发行与账本补齐 | 本地核心流程已验证 | 实现资产初始化、首次分配、后续铸造、发行策略审批、发行上限和供应量对账。补齐冻结、部分结算、释放及按权限查询。验证重复初始化、跨社区审批拒绝、并发额度竞争、批量失败回滚，以及独立连接下的并发扣款和幂等。 |
| M2 个人钱包支付 | 本地核心流程已验证 | 接通应用凭证、建单、Rice 确认页和查单。使用测试积分验证应用隔离、到期、余额不足、并发确认只扣一次，以及确认响应丢失后的查单和交付去重。 |
| M3 金库多签 | 本地核心流程已验证 | 在发行审批的基础上接入独立的账户支出策略、批量提案和执行。验证重复签署、策略换版、提案过期、并发达标只入账一次，以及批准的冻结不能被超额划扣。 |
| M4 旧稻米迁移与切换 | 本地切换与部分回放已验证 | 演练暂停旧账本写入、期初入账、逐账户对账和切换。核对可用余额、未结冻结、历史供应量和旧交易映射，验证旧任务仍可结算或退款。新账本有实际入账后，回退前先停止写入并回放或对账。 |

本地已验证数据库切换、旧写入拦截、切换后继续发放旧任务奖励和退回旧活动报名费，以及将普通赠送和业务冻结结果回放到旧账本。旧账本无法表达的交易由自动回放拒绝，回退报告保留差异供进一步处理。测试环境切换和正式运维流程仍待验证。

## 测试环境切换演练

先部署包含 Point 迁移的 Rice 和结账页版本的 rice-front。确认测试环境入口将 `/v1` 和 `/api` 路由到 Rice，将 `/point-checkout` 路由到 rice-front。Rice 的 `POINT_CHECKOUT_ORIGIN` 指向测试前端。迁移完成后，在测试库执行以下操作。正式切换前使用同样流程演练。

1. 暂停应用和后台任务的资金写入，并备份测试库。运行 `bin/rice eval 'Rice.Release.point_ledger("audit")'`，核对发行总量、未结冻结及异常账户。
2. 经社区治理授权后，以环境变量 `POINT_BOOTSTRAP` 提供 JSON，包含 `community_id`、`code`、`threshold`、`signers` 和可选 `supply_cap`。运行 `bin/rice eval 'Rice.Release.point_ledger("bootstrap")'`，记录返回的资产 ID。
3. 将资产 ID 设为 `POINT_CUTOVER_ID`。运行 `bin/rice eval 'Rice.Release.point_ledger("activate")'`，核对结果后恢复业务写入。数据库切换标记会阻止旧余额和流水继续写入。
4. 检查个人和节点钱包、旧任务发奖、旧活动退款和新转账。验证第三方建单、浏览器确认及服务端查单。
5. 演练回退时重新暂停资金写入。运行 `bin/rice eval 'Rice.Release.point_ledger("report")'`，检查两边对账、账户差异、未结冻结和交易清单。若尚无新交易，执行 `rollback-before-writes`。可回放时，将报告中按序排列的交易 ID 保存为 JSON 数组，通过 `POINT_REVIEWED_TRANSACTIONS` 传入，再执行 `rollback-replay`。回放会拒绝清单变化和旧账本无法表达的交易。回放成功后核对旧账本并恢复写入。

### 测试商户配置

先用 `POINT_WALLET` 传入含 `point_id`、`owner_type`（`user` 或 `node`）和 `owner_id` 的 JSON，执行 `bin/rice eval 'Rice.Release.point_ledger("ensure-wallet")'` 获取收款账户 ID。

使用 `POINT_PAYMENT_APP` 传入包含 `name`、`payee_account_id` 和 `return_url` 的 JSON，执行 `bin/rice eval 'Rice.Release.point_ledger("register-payment-app")'`。命令一次性返回应用 ID 和明文凭证。使用私有终端接收输出，将凭证交由应用服务端保管。后续设置 `POINT_PAYMENT_APP_ID`，通过同一入口执行 `rotate-payment-credential`、`disable-payment-app` 或 `enable-payment-app`。

### 测试金库配置

为节点创建 Point 钱包后，由社区治理授权运维人员初始化首版支出策略。用 `POINT_SPEND_POLICY` 提供包含 `point_id`、`account_id`、`threshold` 和 `signers` 的 JSON，执行 `bin/rice eval 'Rice.Release.point_ledger("bootstrap-spend-policy")'`。随后用当前签署人身份通过 `/v1/points/{point_id}/spend-proposals` 提交和批准测试支出。重复初始化会被拒绝，已有策略的换版和停用通过提案审批执行。

### Nomad 发布检查点

共享测试环境当前基线为 `dev-rice` job 版本 25，镜像 `rice:main-c6b34f4`，以及 `dev-rice-front` job 版本 36，镜像 `rice-front:main-ede1c7c`。发布前重新读取运行状态，记录实际镜像摘要与 job 版本。两个候选镜像分别使用独立的固定标签，禁止使用 `latest` 或推广生产标签。

1. 从两份 `codex/community-points` 工作区构建候选镜像。将测试环境 Rice job 配置中的 `/v1` 路由和 `POINT_CHECKOUT_ORIGIN` 纳入候选。对两个 job 使用候选镜像参数分别执行 `nomad job plan`，核对只影响 `dev-rice` 和 `dev-rice-front`。
2. 先更新 `dev-rice`。等待 prestart 的 `migrate` 和应用健康检查通过，并确认测试库存在 Point 表、切换标记表仍为空。此时旧账本继续作为业务账本。
3. 更新 `dev-rice-front`。检查站点、`/v1/payment-intents` 的凭证校验及结账页路由，再用单独的测试积分资产验证付款。只有网关和支付验证通过后才安排旧稻米切换演练。
4. 切换前保留旧镜像、旧 job 配置和测试库备份。切换标记为空时可恢复旧镜像。标记生效后先按数据库回退流程核对和恢复旧账本写入，再恢复旧应用版本。
